# k6-Lasttest – Anleitung (Aufgabe 2)

> **Modul:** Orchestrierung & Observability · **Aufgabe 2**
> **Repositories:** [`MikeGarda/vsc-ops`](https://github.com/MikeGarda/vsc-ops) (k6-Manifeste) · [`MikeGarda/user_mgmt_service`](https://github.com/MikeGarda/user_mgmt_service) (App, `POST /users/register`)
> **Werkzeug:** [k6](https://k6.io/) (`grafana/k6:latest`), ausgeführt als Kubernetes-Job im Namespace `monitoring`

Diese Anleitung beschreibt, wie der k6-Lasttest gegen den `user_mgmt_service`
aufgebaut ist und wie er manuell im Cluster gestartet wird.

---

## 1. Zweck

Der Test erzeugt kontrolliert steigende (und wieder abfallende) Last auf den
Registrierungs-Endpunkt `POST /users/register` und prüft dabei zwei Dinge:

- **Funktionale Korrektheit unter Last** – jede Registrierung muss mit
  `201 Created` und einer User-ID in der Antwort quittiert werden.
- **Performance-Schwellenwerte** – Fehlerquote und Antwortzeit dürfen
  definierte Grenzen nicht überschreiten.

Der Test dient ausserdem als Lastquelle, um den in `helm/templates/hpa.yaml`
konfigurierten HorizontalPodAutoscaler des Backends zu verifizieren
(Skalierung ab 70 % CPU-Auslastung, siehe `helm/values.yaml`).

## 2. Dateien im Verzeichnis `k6/`

| Datei | Kind | Zweck |
| --- | --- | --- |
| `k6-script.yaml` | `ConfigMap` (`k6-scripts`) | Enthält das eigentliche Testskript `script.ts` als Datei-Eintrag |
| `k6-staging.yaml` | `Job` (`k6-staging`) | Führt das Skript gegen `http://backend.user-mgmt-staging:8080` aus |
| `k6-prod.yaml` | `Job` (`k6-prod`) | Führt das Skript gegen `http://backend.user-mgmt-prod:8080` aus |

Alle drei Manifeste liegen im Namespace `monitoring` – demselben Namespace,
in dem auch der Prometheus-/Grafana-Stack läuft (siehe
[`docs/Prometheus.md`](Prometheus.md)). Die `NetworkPolicy allow-monitoring`
(`helm/templates/networkpolicy.yaml`) lässt eingehenden Traffic aus
`monitoring` auf den Backend-Port zu – dieselbe Freigabe, die Prometheus zum
Scrapen nutzt, ermöglicht auch die HTTP-Aufrufe des k6-Jobs gegen Staging/Prod.

## 3. Aufbau des Testskripts (`k6-script.yaml` → `script.ts`)

Das Skript ist in TypeScript geschrieben (k6 kann `.ts` direkt ausführen)
und liegt als einzelner `data`-Eintrag `script.ts` in der ConfigMap
`k6-scripts`.

### 3.1 Konfiguration (`options`)

```ts
export const options = {
  scenarios: {
    register_ramp: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '1m', target: 5 },   // sanfter Einstieg
        { duration: '2m', target: 20 },  // steigende Last
        { duration: '2m', target: 50 },  // Ramp-up zum Peak
        { duration: '3m', target: 50 },  // Peak-Last halten
        { duration: '2m', target: 0 },   // kontrollierter Abbau
      ],
      gracefulRampDown: '30s',
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.05'],
    'http_req_duration{endpoint:register}': ['p(95)<1500'],
  },
};
```

- **Executor `ramping-vus`**: die Anzahl virtueller User (VUs) wird über die
  Zeit gesteigert und wieder reduziert – realistischer als eine fixe VU-Zahl.
  Gesamtlaufzeit: **10 Minuten** (1+2+2+3+2 Min.), Peak bei **50 VUs**.
- **`gracefulRampDown: '30s'`**: laufende Iterationen dürfen beim Herunterfahren
  noch 30 s zu Ende laufen, statt hart abgebrochen zu werden.
- **`thresholds`**: k6 markiert den Testlauf als fehlgeschlagen, wenn
  - mehr als 5 % aller Requests fehlschlagen (`http_req_failed`), oder
  - der p95-Wert der Antwortzeit für den `register`-Endpunkt über 1500 ms liegt.

### 3.2 Testdaten & Ablauf (`default function`)

```ts
export default function () {
  const uniqueSuffix = `${__VU}-${__ITER}-${randomString(8)}`;
  const payload = JSON.stringify({
    firstName: 'Load',
    lastName: 'Test',
    email: `load-test-${uniqueSuffix}@example.ch`,
    password: `Passw0rd!${uniqueSuffix}`,
  });

  const res = http.post(`${BASE_URL}/users/register`, payload, {
    headers: { 'Content-Type': 'application/json' },
    tags: { endpoint: 'register' },
  });

  const success = check(res, {
    'Status ist 201 Created': (r) => r.status === 201,
    'Antwort enthaelt eine User-ID': (r) => !!JSON.parse(r.body as string).id,
  });

  if (!success) registrationErrors.add(1);
  sleep(1);
}
```

- **`BASE_URL`** kommt aus der Umgebungsvariable `__ENV.BASE_URL` (Default
  `http://localhost:8080` für lokale Läufe) und wird pro Umgebung im
  jeweiligen `Job`-Manifest gesetzt (siehe Abschnitt 4).
- **Eindeutige E-Mail pro Iteration**: `User.email` hat einen
  Unique-Constraint in der Datenbank (`User.java`); `${__VU}-${__ITER}-<random>`
  garantiert, dass jede Iteration eine neue, gültige Registrierung erzeugt
  statt an `409 Conflict` zu scheitern.
- **Tag `endpoint: register`**: erlaubt es, die HTTP-Metrik im Threshold
  gezielt auf diesen einen Endpunkt einzuschränken.
- **Custom-Metric `registration_errors`** (`Counter`): ergänzt die
  eingebauten k6-Metriken um eine fachliche Kennzahl – wie viele
  Registrierungen inhaltlich (Status oder fehlende ID) fehlgeschlagen sind,
  unabhängig vom reinen Netzwerk-/HTTP-Fehler.
- **`sleep(1)`**: 1 Sekunde Pause zwischen den Iterationen pro VU, um eher
  reales Nutzerverhalten statt maximalen Durchsatz zu simulieren.

## 4. Aufbau der Jobs (`k6-staging.yaml` / `k6-prod.yaml`)

Beide Dateien sind bis auf Namen und `BASE_URL` identisch aufgebaut:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: k6-staging
  namespace: monitoring
spec:
  template:
    spec:
      containers:
        - name: k6-staging
          image: grafana/k6:latest
          args: [run, /scripts/script.ts]
          env:
            - name: BASE_URL
              value: "http://backend.user-mgmt-staging:8080"
          volumeMounts:
            - name: scripts
              mountPath: /scripts
          resources:
            requests: {cpu: 250m, memory: 256Mi}
            limits:   {cpu: "1",  memory: 512Mi}
      restartPolicy: Never
      volumes:
        - name: scripts
          configMap:
            name: k6-scripts
  backoffLimit: 1
```

| Element | Erläuterung |
| --- | --- |
| `image: grafana/k6:latest` | Offizielles k6-Image, enthält die k6-CLI |
| `args: [run, /scripts/script.ts]` | Startet den Testlauf mit dem gemounteten Skript |
| `env.BASE_URL` | Zeigt auf den `backend`-Service in `user-mgmt-staging` bzw. `user-mgmt-prod` – **cross-namespace** Cluster-DNS-Name (`<service>.<namespace>`) |
| `volumes.scripts` (ConfigMap `k6-scripts`) | Bindet `script.ts` aus der ConfigMap unter `/scripts/script.ts` ein |
| `restartPolicy: Never` + `backoffLimit: 1` | Ein Lasttest soll bei einem Fehlschlag nicht endlos neu gestartet werden; maximal ein Retry |
| `resources` | 250m–1 CPU / 256–512Mi – der k6-Pod selbst muss ebenfalls in die `ResourceQuota` des Namespace passen |

> **Hinweis:** Der `Job` ist unveränderlich – ein erneutes `kubectl apply`
> auf einen bereits gelaufenen Job schlägt fehl. Vor einem neuen Lauf muss
> der alte Job gelöscht werden (siehe Abschnitt 5).

## 5. Anwendung

### 5.1 Voraussetzung

`kubectl`-Kontext zeigt auf den DOKS-Cluster (`teko-doks`), Namespace
`monitoring` existiert bereits (wird u. a. vom Monitoring-Stack angelegt,
siehe `application-monitoring.yaml`).

### 5.2 Skript (ConfigMap) einspielen/aktualisieren

```bash
kubectl apply -f k6/k6-script.yaml
```

Das ist bei jeder Änderung an `script.ts` nötig, bevor ein neuer Job
gestartet wird.

### 5.3 Test gegen Staging starten

```bash
# ggf. vorherigen Lauf entfernen (Job ist unveränderlich):
kubectl delete job k6-staging -n monitoring --ignore-not-found

kubectl apply -f k6/k6-staging.yaml

# Live-Logs mitverfolgen (Ausgabe inkl. Thresholds/Summary am Ende):
kubectl logs -n monitoring job/k6-staging -f
```

### 5.4 Test gegen Prod starten

Analog mit `k6-prod.yaml`:

```bash
kubectl delete job k6-prod -n monitoring --ignore-not-found
kubectl apply -f k6/k6-prod.yaml
kubectl logs -n monitoring job/k6-prod -f
```

> Ein Lasttest gegen Prod sollte bewusst und mit Vorsicht eingesetzt werden
> (echte Last auf die Produktionsumgebung).

### 5.5 Ergebnis prüfen

- **k6-Zusammenfassung** in den Job-Logs: `http_req_failed`, p95 von
  `http_req_duration{endpoint:register}`, sowie die Custom-Metric
  `registration_errors`. Ein "✓"/"✗" je Threshold zeigt Erfolg/Fehlschlag.
- **HPA-Verifikation** parallel zum Lauf:
  ```bash
  kubectl get hpa backend -n user-mgmt-staging -w
  ```
  Bei steigender CPU-Last sollte die Replica-Zahl Richtung `maxReplicas: 3`
  wachsen (siehe `helm/templates/hpa.yaml`).
- **Grafana**: Request Rate / Response Time / Error Rate des Backends lassen
  sich während des Laufs im Dashboard `user_mgmt_service` mitverfolgen
  (siehe [`docs/Prometheus.md`](Prometheus.md), Abschnitt 4.4).

### 5.6 Aufräumen

```bash
kubectl delete job k6-staging -n monitoring --ignore-not-found
kubectl delete job k6-prod -n monitoring --ignore-not-found
```

Die ConfigMap `k6-scripts` kann bestehen bleiben, da sie von keinem laufenden
Job mehr referenziert wird, sobald die Jobs gelöscht sind.

## 6. Anpassungen

| Änderung | Wo |
| --- | --- |
| Ziel-URL / Umgebung | `env.BASE_URL` in `k6-staging.yaml` / `k6-prod.yaml` |
| Last-Profil (VUs, Dauer der Stufen) | `options.scenarios.register_ramp.stages` in `script.ts` |
| Erfolgs-Schwellenwerte | `options.thresholds` in `script.ts` |
| Getesteter Endpunkt / Payload | `export default function()` in `script.ts` |
| Ressourcen des k6-Pods | `resources` im jeweiligen `Job`-Manifest |

Nach jeder Änderung an `script.ts` muss die ConfigMap neu angewendet
(`kubectl apply -f k6/k6-script.yaml`) und ein neuer Job gestartet werden.

## 7. Ausblick: Integration in die CI-Pipeline

Aktuell wird der Test **manuell** ausgeführt. In
`user_mgmt_service/.github/workflows/deploy-staging.yaml` ist bereits ein
(auskommentierter) Job-Slot `load-test` vorbereitet, der nach der
Promotion auf Staging automatisch

1. auf den ArgoCD-Sync wartet,
2. den k6-Job gegen Staging ausführt,

um den Lasttest zu einem festen, automatisierten Bestandteil der
Staging-Pipeline zu machen (siehe README, Tabelle „Vorbereitung auf die
Aufgaben 2–6").
